# Результаты тестирования

Состояние на 2026-11-09, версии компонентов: Rauthy 0.37.2, Caddy 2.11.9, s6-overlay 3.2.3.2, Go 1.24.

## Что проверено

### Автотесты (`make test`: `go vet` + `go test -race`)

| Пакет | Что покрыто |
|---|---|
| `config` | разбор единого `guard.yml` (все секции, ошибки с номером строки, подсказка для старой схемы из нескольких файлов, валидность `config.example/` и демо), значения по умолчанию, отказ от неизвестных полей в любой секции, сбор всех ошибок за один проход, дубликаты имён/доменов/`client_id`, правила режимов `proxy`/`app`, разрешение `tls.mode: auto` |
| `rauthy` | формат запросов к Admin API (поля create/update, заголовок `API-Key`, коды ошибок), рендер `config.toml` (экранирование, порты, `rp_origin`), `api_keys.json`; полный цикл синхронизации на фейковом Rauthy: создание → no-op → исправление дрейфа → disable/delete при удалении → повторное включение; клиенты, созданные вручную, не трогаются |
| `caddy` | Caddyfile для всех режимов TLS и авторизации, порядок удаления заголовков до `forward_auth`, ограничение Admin UI, fallback на локальный CA, редиректы для нестандартного порта, загрузка через admin API |
| `backup` | архив → восстановление (берётся самый свежий бэкап БД, lock-файлы не попадают, права `0600`), отказ восстанавливать поверх данных без `--force`, ротация |
| `app` | первый запуск (секреты `0600` в каталоге `0700`, bootstrap-файлы, одинаковый пароль при прерванном первом старте), повторный запуск без bootstrap, откат на рабочую конфигурацию при ошибке, запрет смены RP ID; демон на фейковых Rauthy и Caddy: создание клиентов, горячее добавление приложения, last-good Caddyfile, ошибка конфигурации в `/health` (наружу только статус), удаление одноразового пароля после первого входа админа |

### Проверка с настоящим Caddy 2.11.9

Каждый сгенерированный Caddyfile (`acme`, `custom`, `local-ca`, нестандартный порт, `trusted_proxies`) прошёл `caddy adapt --validate`. Затем Caddy был запущен со сгенерированным конфигом против фейкового forward-auth и echo-upstream, порты эмулировали `docker -p 18443:443 -p 18080:80`:

| Сценарий | Результат |
|---|---|
| Запрос без сессии в proxy-приложение | 302 на страницу входа, upstream не вызван |
| Сессия + поддельные `X-Guard-User`/`X-Guard-Roles` от клиента | upstream получил только значения от forward-auth, подделка удалена |
| forward-auth получает `X-Forwarded-Method/Uri/Host/Proto` и Cookie | да |
| `none`-приложение с поддельным `X-Guard-User` | заголовок удалён |
| `/.guard/callback?code&state` | переписан на `/auth/v1/clients/<id>/forward_auth/callback`, `Set-Cookie` вернулся браузеру |
| `/auth/v1/admin*` с адреса вне `allow_from` | 403; остальные пути Rauthy проходят |
| `/health` снаружи | проксируется на публичный вариант |
| `http://auth…/.guard/ca.crt` | 200, `application/x-x509-ca-cert`, совпадает с корнем CA |
| HTTP → HTTPS с публичным портом 18443 | 308 на `https://<host>:18443/…` для auth и приложений |
| `/.guard/logout` | 302 на `/auth/v1/oidc/logout` |
| Горячая загрузка нового Caddyfile через admin API | новое приложение доступно без перезапуска |
| Загрузка битого Caddyfile | 400, старая конфигурация продолжает работать |
| Ответы без заголовка `Server`, с `X-Content-Type-Options` и `Referrer-Policy` | да |

### Скрипты s6

`bash -n` и `shellcheck` без замечаний.

## Что не проверено здесь и требует прогона на целевой машине

Образ в этой среде не собирался: нет доступа к `ghcr.io` и Docker Hub. Rauthy тоже не запускался. Интеграция с его API проверена по исходному коду 0.37.2 (структуры запросов, права API-ключей, bootstrap, forward-auth) и тестами на фейковом сервере. Перед приёмкой выполните:

1. `make image`, затем `examples/local-demo`: первый запуск, вход админа по одноразовому паролю, регистрация Passkey, вход по Passkey, второй Passkey и его удаление.
2. Proxy-приложение `whoami`: полный цикл входа через forward-auth, заголовки `X-Guard-*`, выход через `/.guard/logout`.
3. SPA и Express из `examples/` в режиме `app`.
4. Перезапуск контейнера: данные и Passkeys на месте; `kill` процесса Rauthy внутри контейнера приводит к его перезапуску без перезапуска контейнера.
5. `guard-sync backup` → `restore` на новый volume → вход работает.
6. `docker stats` под нагрузкой входами с `--memory=256m`, замер RSS каждого процесса.
7. ACME на реальном домене (лучше со staging CA: `tls.acme.ca`).
8. Браузеры: Chrome, Safari, Firefox на macOS, iOS, Android и Windows.
