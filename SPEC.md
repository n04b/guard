# Техническое задание
## Guard — лёгкий Auth Server для небольших веб-проектов

**Версия:** 2.1
**Статус:** Реализовано (первая версия), см. README.md и docs/testing.md
**Изменения в 2.1 (по итогам реализации):** режим `proxy` реализован встроенным forward-auth Rauthy без oauth2-proxy; Caddy получает конфигурацию в виде Caddyfile через admin API; порты в `server.yml` — публичные (внутри контейнера всегда 80/443); глобальное отключение пароля заменено обязательным Passkey для отдельных приложений и админов; регистрация — `closed` / `open` (приглашения заменены командой `guard-sync user add`); уточнены поля YAML (раздел 8); добавлены команды `guard-sync` и известные ограничения.
**Изменения в 2.0 относительно 1.0:** Keycloak + H2 заменены на Rauthy (SQLite); NGINX + OpenSSL + ACME-клиент заменены на Caddy; убраны отдельные Node.js/Express и React; добавлен супервизор s6-overlay; явно разделены режимы авторизации; self-signed заменён локальным CA; зафиксирован RP ID; критерии приёмки сделаны измеримыми. Восстановление доступа вынесено из первой версии (см. `TODO.md`).

## 1. Цель проекта

Разработать самостоятельный сервер аутентификации и авторизации, который подключается к небольшим веб-приложениям и даёт им единый вход по Passkeys и паролю.

Приоритеты:

- один Docker-контейнер;
- минимум обязательных настроек;
- никаких обязательных внешних сервисов (SMTP, внешняя БД, внешний OAuth);
- потребление RAM — десятки мегабайт, а не сотни;
- быстрый запуск;
- управление через конфигурационные файлы;
- обслуживание нескольких веб-приложений одновременно.

## 2. Технологический стек

| Компонент | Технология |
|---|---|
| Identity Provider | Rauthy (Rust) |
| База данных | Встроенная в Rauthy (SQLite / Hiqlite), файл в Docker volume |
| Reverse Proxy и TLS | Caddy (автоматический HTTPS, ACME, внутренний CA) |
| Синхронизация конфигурации | `guard-sync` — небольшая утилита, предпочтительно Go (один статический бинарник) |
| Супервизор процессов | s6-overlay v3 |
| UI входа и кабинет пользователя | Встроенные UI Rauthy с брендированием |
| Контейнеризация | Docker |
| Конфигурация | YAML (интерфейс Guard) + ENV для секретов |
| Протоколы | OAuth 2.0 (авторизация), OpenID Connect (аутентификация поверх OAuth 2.0) |
| Passkeys | WebAuthn / FIDO2 |

Отдельные Node.js/Express и React в составе сервера не используются. Примеры интеграции для React и Express остаются в документации (раздел 9).

## 3. Архитектура

```text
            ┌──────────────────────── контейнер guard ───────────────────────┐
 :80/:443 ─▶│ Caddy ──▶ auth.example.com ──▶ Rauthy (127.0.0.1)              │
            │   │                                                             │
            │   ├──▶ app1.example.com ──(forward_auth, если mode: proxy)──▶ upstream app1
            │   └──▶ app2.example.com ─────────────────────────────────────▶ upstream app2
            │                                                                 │
            │ guard-sync: YAML ──▶ Admin API Rauthy (клиенты)                 │
            │                 └──▶ Admin API Caddy (маршруты, TLS)            │
            │ s6-overlay: запуск, перезапуск, остановка всех процессов        │
            └─────────────────────────────────────────────────────────────────┘
```

### 3.1. Rauthy

Отвечает за:

- регистрацию и управление пользователями;
- аутентификацию по паролю и Passkeys;
- хранение и проверку паролей;
- регистрацию, проверку и удаление Passkeys;
- пользовательские сессии;
- выпуск Access Token, ID Token и Refresh Token;
- роли и группы;
- OpenID Connect / OAuth 2.0;
- защиту от перебора паролей;
- резервное копирование своей БД.

Rauthy слушает только `127.0.0.1` внутри контейнера. Снаружи он доступен только через Caddy.

### 3.2. Caddy

Единый reverse proxy для всех подключённых приложений:

- принимает HTTP и HTTPS;
- маршрутизирует запросы к приложениям по домену;
- обслуживает несколько доменов и поддоменов;
- поддерживает WebSocket;
- передаёт `X-Forwarded-*` заголовки;
- выпускает и продлевает сертификаты (раздел 7);
- для приложений в режиме `proxy` проверяет авторизацию через `forward_auth` (раздел 3.5);
- принимает изменения конфигурации через Admin API без перезапуска.

Admin API Caddy слушает только `127.0.0.1` (или unix-socket) и наружу не публикуется.

### 3.3. guard-sync

Утилита, которая превращает YAML Guard в состояние Rauthy и Caddy.

Обязанности:

- читать и валидировать YAML (схема, обязательные поля, уникальность доменов и `client_id`);
- приводить OIDC-клиентов, роли, группы и парольную политику в Rauthy к описанию в YAML через Admin API (по API-ключу, созданному при первом запуске);
- генерировать `config.toml` Rauthy при каждом старте контейнера (`guard-sync init`);
- собирать Caddyfile и загружать его через admin API Caddy;
- следить за изменениями файлов (опрос раз в 2 секунды, включая файлы `custom`-сертификатов) и по сигналу `SIGHUP`; полная сверка с Rauthy раз в 5 минут исправляет ручные изменения;
- применять изменения безопасно: при ошибке валидации или применения остаётся предыдущая рабочая конфигурация;
- сохранять последний принятый Caddyfile в `/data/guard/Caddyfile`, Caddy стартует с ним;
- команды: `init`, `run`, `check [--caddyfile]`, `healthcheck`, `backup`, `restore`, `user add`, `user set-password`, `version`.

`guard-sync` не хранит пароли, не реализует WebAuthn и не выпускает токены.

**Источник истины:**

| Данные | Где хранятся |
|---|---|
| Приложения, OIDC-клиенты, redirect URI, маршруты, TLS, политики безопасности | YAML |
| Пользователи, Passkeys, пароли, сессии, членство в группах | БД Rauthy |
| Перечень ролей и групп | YAML (создаются при синхронизации); назначение пользователям — в Admin UI Rauthy |

Изменения применяются как diff. `guard-sync` никогда не переимпортирует realm целиком и не трогает пользовательские данные.

### 3.4. s6-overlay

PID 1 контейнера. Обязанности:

- порядок запуска: Caddy (с last-good конфигурацией) → Rauthy → `guard-sync` (после healthy Rauthy);
- перезапуск упавшего процесса без перезапуска всего контейнера;
- корректная остановка всех процессов по `SIGTERM` в пределах таймаута;
- если Rauthy не поднимается N раз подряд, контейнер завершается с ненулевым кодом, чтобы сработала restart policy Docker.

### 3.5. Режимы авторизации приложений

Каждое приложение указывает режим явно:

| `auth.mode` | Кто проверяет авторизацию | Что делает Guard |
|---|---|---|
| `proxy` | Caddy через `forward_auth` | Неавторизованный пользователь уходит на вход; upstream получает запрос только с действующей сессией и заголовки с идентичностью (`X-Guard-User`, `X-Guard-Email`, `X-Guard-Groups`). Входящие заголовки `X-Guard-*` от клиента удаляются |
| `app` | Само приложение (OIDC-клиент) | Создаёт OIDC-клиента и проксирует трафик без проверки. Приложение обязано проверять подпись, `iss`, `aud`, `exp` |
| `none` | Никто | Только проксирование (публичные приложения) |

В режиме `proxy` upstream должен принимать запросы только от Guard (внутренняя сеть Docker), иначе заголовки `X-Guard-*` можно подделать.

Реализация `proxy`: Caddy `forward_auth` → `GET /auth/v1/clients/<client_id>/forward_auth?redirect_state=302` (Rauthy). Без сессии Rauthy возвращает 302 на страницу входа; после входа callback `/.guard/callback` на домене приложения переписывается на `/auth/v1/clients/<client_id>/forward_auth/callback`, и Rauthy ставит `__Host-` cookie, привязанные к сессии Guard. Заголовки пользователя Rauthy отдаёт в ответе forward-auth, Caddy копирует их в запрос к upstream (`copy_headers`). Отдельный oauth2-proxy не нужен. Выход: `/.guard/logout` на домене приложения.

## 4. Аутентификация

### 4.1. Passkeys

Основной способ аутентификации.

Требования:

- регистрация Passkey;
- вход по Passkey;
- несколько Passkeys у одного пользователя;
- просмотр и удаление Passkeys в кабинете пользователя;
- поддержка биометрии устройства (Face ID, Touch ID, Windows Hello и аналоги) и аппаратных ключей;
- обязательная проверка пользователя (User Verification).

Биометрию проверяет устройство пользователя. Система не получает и не хранит биометрические данные.

**RP ID.** WebAuthn Relying Party ID задаётся в `server.yml` (`webauthn.rp_id`) и после первой регистрации Passkey считается неизменяемым. Если его сменить, все зарегистрированные Passkeys станут недействительны. `guard-sync` отказывается применять изменение `rp_id` без флага `--i-understand-passkeys-will-break`.

По умолчанию `rp_id` совпадает с хостом сервера авторизации (`auth.example.com`).

### 4.2. Парольная аутентификация

Альтернативный вход по e-mail и паролю.

Требования:

- обязательный Passkey для отдельного приложения (`auth.require_passkey`) и для администраторов (`admin.require_passkey`); глобального отключения пароля в Rauthy нет — пользователь может сам перевести аккаунт в режим «только Passkey» в кабинете;
- минимальная длина и политика сложности пароля;
- ограничение неудачных попыток и защита от перебора;
- смена пароля в кабинете пользователя.

### 4.3. Регистрация пользователей

Режим задаётся в `security.yml`:

- `closed` — пользователей создаёт администратор (по умолчанию): `guard-sync user add <email>` печатает одноразовый пароль, либо Admin UI;
- `open` — открытая регистрация, опционально с ограничением по домену e-mail. Требует SMTP: Rauthy отправляет ссылку для установки пароля.

### 4.4. Выход из системы

- RP-initiated logout (OIDC) обязателен для всех клиентов;
- back-channel logout — для клиентов, которые его поддерживают (`auth.backchannel_logout_uri`; Rauthy поддерживает);
- в режиме `proxy` выход по `/.guard/logout` на любом домене приложения завершает сессию и в Guard.

### 4.5. Первый администратор

При первом запуске с пустой БД создаётся администратор с e-mail из `server.yml` (`admin.bootstrap_email`) и случайным одноразовым паролем. Пароль записывается в `/data/secrets/bootstrap-admin.txt` с правами `0600` и не выводится в логи. Для доступа к Admin UI администратор обязан зарегистрировать Passkey (`admin.require_passkey`, по умолчанию `true`); файл удаляется `guard-sync` после первого успешного входа.

## 5. База данных

Встроенная БД Rauthy (SQLite / Hiqlite).

Требования:

- файл БД в постоянном Docker volume (`/data/rauthy`);
- сохранение данных после перезапуска и пересоздания контейнера;
- никакого отдельного контейнера БД;
- консистентные резервные копии без остановки сервиса средствами Hiqlite (раздел 13);
- восстановление из резервной копии.

Single-node конфигурация. Кластеризация и HA в первую версию не входят.

## 6. Docker и запуск

Один образ, внутри:

- Rauthy;
- Caddy;
- `guard-sync`;
- s6-overlay;
- шаблоны конфигурации по умолчанию.

Требования:

- запуск одной командой;
- автоматический запуск всех компонентов;
- корректное завершение по `SIGTERM`;
- перезапуск отдельных упавших процессов (раздел 3.4);
- единый вывод логов в stdout/stderr с префиксом компонента;
- Docker `HEALTHCHECK`;
- данные — только в volume `/data`, конфигурация — в `/config` (read-only mount допускается).

Внутри контейнера Caddy всегда слушает 80 и 443. `server.http_port` / `server.https_port` — публичные порты (для нестандартного: `-p 8443:443` и `https_port: 8443`).

Пример запуска:

```bash
docker run -d --name guard \
  -p 80:80 -p 443:443 \
  -v guard-data:/data \
  -v ./config:/config:ro \
  --memory=256m \
  guard:latest
```

## 7. TLS

### 7.1. Режимы

Один параметр `tls.mode`:

| Режим | Поведение |
|---|---|
| `custom` | Сертификат и ключ пользователя из `/certs` |
| `acme` | Let's Encrypt (или другой ACME CA) через Caddy, HTTP-01 / TLS-ALPN-01 для каждого домена |
| `local-ca` | Внутренний CA Caddy: Guard выпускает сертификаты от собственного корневого сертификата. Корневой сертификат экспортируется в `/data/caddy/root.crt` для установки на устройства |
| `auto` | `custom`, если файлы есть; иначе `acme`, если `acme.email` задан и домены публичные; иначе `local-ca` |

Голый self-signed не используется: браузеры отключают WebAuthn на сайтах с ошибкой сертификата, и Passkeys не заработают. С `local-ca` после установки корневого сертификата на устройство ошибок нет.

Если в режиме `acme` выпуск для публичного домена не удался, Guard **не** переключается на `local-ca` молча. Переключение возможно только при `tls.acme.allow_fallback: true`, с предупреждением в логах и в `/health`.

Wildcard-сертификаты (DNS-01) в первую версию не входят.

### 7.2. Продление

В режимах `acme` и `local-ca` Caddy сам продлевает сертификаты и применяет их без перезапуска. Срок действия сертификатов отображается в `/health`.

### 7.3. HTTPS

- весь HTTP перенаправляется на HTTPS, кроме ACME-проверок;
- HSTS включается в режимах `custom` и `acme`;
- для локальной разработки допускается `localhost` (WebAuthn работает в secure context localhost).

## 8. Конфигурация

Основной способ управления — файлы. Admin UI Rauthy нужен только для работы с пользователями.

Структура:

```text
guard/
├── config/
│   ├── server.yml
│   ├── tls.yml
│   ├── security.yml
│   └── applications/
│       ├── app1.yml
│       └── app2.yml
├── certs/               # только для tls.mode: custom
│   ├── fullchain.pem
│   └── privkey.pem
└── docker-compose.yml
```

Volume `/data`:

```text
/data/
├── rauthy/              # БД (Hiqlite), state_machine/backups — автоматические бэкапы
├── caddy/               # сертификаты, ACME-аккаунт, локальный CA
├── guard/               # state.json, последний Caddyfile, config.toml Rauthy
├── backups/             # архивы guard-sync backup
└── secrets/             # ключи, API-ключ, секреты клиентов, bootstrap-пароль (0600)
```

Полные шаблоны с комментариями: `config.example/` в репозитории. Кратко:

`server.yml`:

```yaml
server:
  hostname: auth.example.com
  http_port: 80                # публичные порты
  https_port: 443
  trusted_proxies: []          # CIDR прокси перед Guard

webauthn:
  rp_id: auth.example.com      # после первой регистрации Passkey не менять
  rp_name: Guard

admin:
  bootstrap_email: admin@example.com
  allow_from: [127.0.0.1/32, ::1/128, 100.64.0.0/10]
  require_passkey: true

smtp:
  enabled: false               # host, port, username, password_env, from, tls_mode

backup:
  cron: "0 30 2 * * * *"       # сек мин час день месяц день_недели год
  keep_days: 7

logging:
  level: info
```

`tls.yml`:

```yaml
tls:
  mode: auto                   # custom | acme | local-ca | auto
  custom:
    certificate: /certs/fullchain.pem
    private_key: /certs/privkey.pem
  acme:
    email: admin@example.com
    # ca: https://acme-staging-v02.api.letsencrypt.org/directory
    allow_fallback: false
    fallback_after: 10m
```

`security.yml`:

```yaml
registration:
  mode: closed                 # closed | open (open требует SMTP)
  # allowed_email_domain: example.com

password_policy:
  min_length: 12
  max_length: 128
  require_lowercase: 0
  require_uppercase: 0
  require_digits: 0
  require_special: 0
  not_recently_used: 0
  valid_days: 0

session:
  idle_minutes: 60
  max_hours: 720

hashing:                       # Argon2id; пик памяти ≈ memory_mib × max_parallel_hashes
  memory_mib: 32
  iterations: 3
  parallelism: 2
  max_parallel_hashes: 2

roles: [editor]
groups: [family, team]
```

Защита от перебора паролей встроена в Rauthy (растущие задержки, блокировка IP) и отдельными параметрами не настраивается.

`applications/app1.yml`:

```yaml
application:
  name: app1
  domain: app1.example.com

  upstream:
    host: app1
    port: 3000
    scheme: http               # http | https
    # tls_insecure_skip_verify: false

  auth:
    mode: proxy                # proxy | app | none
    client_id: app1            # по умолчанию = name
    # client_type: public | confidential — для mode app (по умолчанию public)
    # redirect_uris, allowed_origins — только для mode app
    post_logout_redirect_uris: [https://app1.example.com/]
    # backchannel_logout_uri: https://app1.example.com/oidc/backchannel
    scopes: [openid, profile, email, groups]
    restrict_group_prefix: team    # пускать только пользователей с группой team*
    require_passkey: false
    signing_alg: RS256         # RS256 | RS384 | RS512 | EdDSA
    access_token_seconds: 1800

  on_remove: disable           # disable | delete — что делать с клиентом при удалении файла
```

Секрет confidential-клиента генерирует `guard-sync` при создании клиента и записывает в `/data/secrets/clients/<name>.secret` (`0600`). Секреты в YAML не хранятся.

При удалении файла приложения маршрут удаляется сразу, а OIDC-клиент отключается (`disable`) или удаляется (`delete`).

## 9. Подключение веб-приложений

Для каждого приложения задаются: название, домен, upstream, режим авторизации, `client_id`, тип клиента, redirect URI, ограничение по группе.

Процедура подключения: добавить файл в `config/applications/` → `guard-sync` применит его автоматически (или `docker kill -s HUP guard`). Проверка: `docker exec guard guard-sync check`.

Документация и примеры:

- React SPA: public client, Authorization Code + PKCE (например, `oidc-client-ts`);
- Express: confidential client (`openid-client`) и проверка JWT по JWKS (`jose`) с проверкой `iss`, `aud`, `exp`, подписи;
- приложение без OIDC в режиме `proxy`: чтение заголовков `X-Guard-*` и требование принимать трафик только от Guard.

## 10. Безопасность

Обязательно:

- HTTPS для публичного доступа;
- секреты — только в ENV и `/data/secrets` с правами `0600`, не в YAML и не в логах;
- проверка `iss`, `aud`, `exp` и подписи токенов в примерах и в режиме `proxy`;
- защита от перебора паролей;
- PKCE для всех клиентов;
- точное совпадение redirect URI, без wildcard;
- корректный CORS (только домены зарегистрированных приложений);
- защита от CSRF;
- cookie `HttpOnly`, `Secure`, `SameSite=Lax` (или строже);
- удаление входящих `X-Guard-*` заголовков на прокси;
- Admin UI Rauthy доступен только с адресов из `admin.allow_from` (по умолчанию только localhost);
- Admin API Caddy и Rauthy наружу не публикуются;
- пароли, приватные ключи, секреты клиентов и полные токены не попадают в логи.

## 11. Производительность

- один экземпляр каждого компонента, без кластеризации;
- никаких фоновых сервисов кроме Rauthy, Caddy и `guard-sync`;
- параметры хеширования паролей подобраны под лимит памяти контейнера;
- потребление RAM измеряется отдельно для каждого процесса и для контейнера целиком под нагрузкой (логины, обновление токенов).

## 12. Логирование и диагностика

- единый вывод в stdout/stderr, префикс компонента (`[rauthy]`, `[caddy]`, `[sync]`);
- журнал запуска, остановки и перезапусков процессов (s6);
- журнал применения конфигурации: что изменилось, успех или ошибка;
- `/health` на `auth.example.com`: публично — только `ok` / `degraded` / `down`; подробности (состояние процессов, срок сертификатов, время последнего бэкапа и последней синхронизации) — только с адресов из `admin.allow_from`.

## 13. Резервное копирование

- автоматические бэкапы БД Rauthy (Hiqlite) по расписанию `backup.cron`, с ротацией `keep_days`, в `/data/rauthy/state_machine/backups`;
- `guard-sync backup` — архив в `/data/backups`: последний бэкап БД + `/config` + `/data/caddy` (сертификаты и CA) + `/data/secrets` + состояние `guard-sync`;
- `guard-sync restore <архив>` — восстановление на пустой volume (или `--force`); БД восстанавливает Rauthy при следующем старте;
- бэкап делается штатным механизмом Rauthy, а не копированием файла живой БД;
- процедура проверки восстановления описана в документации и выполняется в тестах.

## 14. Критерии приёмки

1. Контейнер запускается одной командой `docker run` (раздел 6).
2. Все процессы стартуют автоматически; до healthy — не более 10 секунд на типовом VPS (2 vCPU).
3. Убитый процесс (Rauthy, Caddy, `guard-sync`) перезапускается без перезапуска контейнера.
4. Данные сохраняются после пересоздания контейнера с тем же volume.
5. Вход по паролю работает.
6. Регистрация и вход по Passkey работают в актуальных Chrome, Safari и Firefox на macOS, iOS, Android и Windows.
7. У одного пользователя может быть несколько Passkeys, их можно удалять.
8. Caddy обслуживает минимум три приложения на разных поддоменах, включая WebSocket.
9. Одна сессия Guard даёт вход во все приложения (SSO); выход завершает сессию.
10. Режимы `proxy`, `app`, `none` работают; в режиме `proxy` неавторизованный запрос не доходит до upstream, подделанный `X-Guard-User` удаляется.
11. Работают TLS-режимы `custom`, `acme`, `local-ca`; провал ACME без `allow_fallback` не приводит к молчаливому переключению.
12. Добавление, изменение и удаление файла приложения применяется без перезапуска контейнера; невалидный YAML не ломает работающую конфигурацию.
13. Admin UI недоступен с адресов вне `admin.allow_from`.
14. Для базовой работы не нужны SMTP, внешняя БД и внешний OAuth-провайдер.
15. Бэкап и восстановление на чистый volume проходят, пользователи и Passkeys после восстановления работают.
16. Контейнер стабильно работает с `--memory=256m` под нагрузкой из раздела 11; фактическое потребление по процессам измерено и указано в результатах тестирования.
17. Секреты, пароли и полные токены не встречаются в логах (проверяется автотестом по логам прогона).
18. Подготовлена документация по установке, настройке и подключению приложений.

## 17. Известные ограничения

- Rauthy не рекомендует discoverable credentials: при входе по Passkey пользователь сначала вводит e-mail (после первого входа он подставляется автоматически).
- Глобально отключить вход по паролю нельзя; вместо этого — `require_passkey` для приложений и админов и аккаунты «только Passkey».
- Внеплановый бэкап БД через API требует сессии администратора, поэтому `guard-sync backup` берёт последний бэкап по расписанию (свежий можно создать в Admin UI → Config → Backups).
- Удаление роли/группы из `security.yml` не удаляет её в Rauthy.
- Файлы `custom`-сертификата должны читаться пользователем uid 10001.
- Rauthy — проект меньше и моложе Keycloak; SAML, LDAP-федерация и сложные политики доступа не поддерживаются.
- Single-node: при отказе диска данные восстанавливаются только из бэкапа.
- Смена `webauthn.rp_id` делает все Passkeys недействительными.
